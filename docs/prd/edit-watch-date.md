# Correct an existing Watch's date

Issue: [#336](https://github.com/Rowan-Paul/opnshelf/issues/336)

Status: Implemented on 2026-10-03 after operator confirmation of the design.

## Agreed behavior

- Owners can correct a Watch's calendar date and time, choose **No date**, or
  give a date and time to a Watch that currently has **No date**.
- The editor starts with the existing value, without resetting it to now.
- A correction changes where the Watch belongs in date-based Activity and
  statistics. Giving it a date includes it at that watch time; clearing its
  date excludes it from those surfaces while retaining it on the Shelf.
- Editing does not create an additional Activity.
- Corrections preserve the Watch and its record key, including imported
  Watches. Import recovery must preserve User corrections (ADR 0042).
- Editing belongs on the existing watch-history surfaces in both the Web App
  and Mobile App. Undated Watches continue to sort after dated Watches under
  ADR 0037.
- Two Watches remain separate even when a correction gives them identical
  media coordinates and timestamps. Editing never merges or deletes another
  Watch.

## Editor behavior on both clients

- Use the User's saved timezone, identify it in the editor, and use it for the
  adjacent watch-history dates too. Both watch-history surfaces and their editors use the saved timezone.
- Reject future timestamps in both the editor and update endpoint. Allow past
  dates without checking the Media Item's release date.
- Every correction uses explicit Save and Cancel, including **No date**.
  Selecting **No date** changes the draft, not the saved Watch.
- An undated Watch opens with **No date** selected. Switching to a dated value
  can seed now for adjustment; it does not save until the User chooses Save.
- An unchanged dated Watch retains its exact timestamp, including seconds.

## Competing edits and historical records

Concurrent User corrections use last successful write wins: the last write
accepted by the server determines the saved value. Network delays mean this
need not be the last button pressed. Do not introduce client revision preconditions or a
conflict-resolution interface. This does not authorize background import
recovery to overwrite a User correction; ADR 0042 still applies.

Live statistics and Activity reflect corrected watch times. Saved Watch Recaps
remain snapshots and are not regenerated by a correction. Trakt Import source
dates and retained outcomes remain historical evidence, with the same Watch
key preserving their association to the corrected Watch.

## Verified constraints

The issue's claim that changing the date necessarily changes the record key is
too broad. Interactive logging uses fresh TIDs (ADR 0009); Trakt Import derives
keys from the original media coordinates and timestamp. Storage identifies a
Watch by owner and record key, and ingestion can update its date at that key.

Normal import recovery checks the original key, so retaining it lets recovery
recognize an already imported Watch after a correction. The import
writer's create-conflict recovery now reads existing records rather than
overwriting their dates. Import indexing leaves existing local Watches intact. See `backend/src/users/import/watch-import-writer.service.ts`.

## Scope and completion

This feature edits the date and time of one existing movie or episode Watch.
It does not add bulk editing or edits to other Watch properties.

No product decisions remain open from the interview. The operator confirmed
the shared understanding. API shape, picker composition, and the
import recovery mechanism are implementation choices subject to this contract.

The identity decision is recorded in
[ADR 0042](../adr/0042-watch-date-corrections-preserve-identity.md). This document
records the agreed product contract, rather than an implementation plan.


## Implementation

- Authenticated `PATCH /movies/history/:trackedMovieId` and
  `PATCH /shows/history/:trackedEpisodeId` accept an explicit `watchedAt`
  instant or `null`. Each lookup is scoped to the current User.
- PDS updates preserve the record key, creation time, and other record fields;
  the local index is refreshed after the PDS write, with ingestion as fallback.
- Web uses the existing Your Activity card; Mobile uses the existing Watch
  history sheet. Failed saves retain the draft for retry. Shared query
  invalidation includes the Shelf, live statistics, Up Next, and Social Activity.
- Regression coverage includes identity and field preservation, ownership,
  validation, No date transitions, unchanged timestamp precision, and import
  recovery with both existing and missing records.
- Mobile changes are JavaScript only. The release version is unchanged, so
  deployment uses an OTA update after operator approval.

## Verification

Required checks passed: root `pnpm typecheck` and `pnpm check`, Web/Mobile/
Backend test suites, Backend build, API generation, and API client typecheck.
The Web and Mobile suites each retain one existing skipped performance test.

Visual checks used the real history and picker components with local fixture
Watches: Web at `http://127.0.0.1:4337/` at desktop and narrow widths, and iOS
27.0 on `/watch-date-verification`. Both dated-to-No-date and No-date-to-dated
saves retained the Watch ID; an unchanged iOS save retained sub-minute precision.
Temporary fixture sources were removed and development servers stopped after
verification. Android was not visually exercised; PDS writes were covered with
mocked backend tests rather than writes to a live account.
