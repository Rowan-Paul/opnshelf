# Native tab images on iOS 27

Checked 19 October 2026 for #528 against Expo Router 58.0.23, react-native-screens 4.30.0, React Native 0.88.0 and the installed iOS 27.1 SDK headers.

**Custom full-color images work in the native tab bar on iOS 27.** A repeat trial on iPhone 18 Pro / iOS 27.0 changed only the remote source from `{ uri: user.avatar }` to `{ uri: user.avatar, width: 28, height: 28, scale: 3 }`, retaining `renderingMode="original"`. All tab contents rendered correctly and the selected Profile tab displayed the remote image in full color at the intended size. [Sized remote-image evidence](../review-assets/native-tabs/ios-native-avatar-sized.png). The initial trial passed a 1024-pixel remote square image without explicit dimensions or scale; that malformed image presentation was not an iOS image capability limitation.

## Supported API

Apple's `UITabBarItem` accepts `image` and `selectedImage`; its selected-image initializer is available from iOS 7. The installed `UITabBarItem.h` explicitly documents using `UIImageRenderingModeAlwaysOriginal` to avoid system recoloring. The newer `UITab.image` dates from iOS 18, and `UITab.selectedImage` from iOS 26.1. These are general `UIImage` properties, not an iOS 27-only avatar feature. [Apple tab item initializer](https://developer.apple.com/documentation/uikit/uitabbaritem/init(title:image:selectedimage:)), [original rendering](https://developer.apple.com/documentation/uikit/uiimage/renderingmode-swift.enum/alwaysoriginal), [UITab image](https://developer.apple.com/documentation/uikit/uitab/image). Availability was confirmed in `UIKit.framework/Headers/UITabBarItem.h` and `UITab.h` in Xcode's installed iPhoneOS 27.1 SDK.

iOS 27 adds `UITabBarController.prominentTabIdentifier`, which controls visual emphasis and placement of a tab. It does not introduce support for custom image content. No dedicated avatar/user-image API was found in the inspected UIKit tab headers. This is a bounded source finding, not a claim about the unidentified Threads post. [Apple prominent tab reference](https://developer.apple.com/documentation/uikit/uitabbarcontroller/prominenttabidentifier)

Expo supports `NativeTabs.Trigger.Icon` with `src` and `renderingMode="original"`. `src` can supply a single image or separate `default` and `selected` sources. A conflicting `sf` or `xcasset` prop takes precedence on iOS, so omit those for the avatar case. Use the same rendering mode for both states. Arbitrary React Native `<Image>`/`<View>` JSX does not transfer through this API. [Expo guide](https://docs.expo.dev/router/advanced/native-tabs/), [SDK 58 reference](https://docs.expo.dev/versions/v58.0.0/sdk/router/native-tabs/), installed `expo-router/build/native-tabs/common/elements.d.ts`, `utils/icon.js` and `NativeTabsView.ios.js`.

## Correct sizing and appearance test

For a remote or local-file URI, the source shape to test is `{ uri: avatarUri, width: 28, height: 28, scale: 3 }`, passed to `src`, with `renderingMode="original"` on the Icon. Here 28 is the trial's logical point size, not an Apple-mandated size; a prepared 84 × 84 pixel image is appropriate at scale 3. Default and selected variants use `src={{ default: normalSource, selected: selectedSource }}`, each carrying its own URI and dimensions. `scale` describes image density; it is not a width/height multiplier in the JSX layout. [React Native image source reference](https://reactnative.dev/docs/image#source)

The installed source explains why dimensions matter:

- `react-native-screens/ios/conversion/RNSConversions-Tabs.mm` transfers source width, height and scale to `RCTImageSource`.
- `ios/helpers/image/RNSImageLoadingHelper.mm` supplies those dimensions to `RCTImageLoader`, with clipping enabled and `RCTResizeModeCenter`, then applies original/template rendering.
- `react-native/Libraries/Image/RCTImageUtils.mm` reduces oversized images to fit a nonzero target in center mode. A zero target requests the largest available size; `RCTImageLoader.mm` also skips its final resize for a zero size.

The successful retry establishes that supplying bounded dimensions resolves the observed iOS tab-bar presentation problem for this synthetic remote image. A follow-up rasterized circular default/selected variants and verified the selected ring on both platforms, using a synthetic square source. Failed-URI fallbacks also rendered correctly on both. [iOS circle](../review-assets/native-tabs/ios-native-avatar-circle.png), [Android circle](../review-assets/native-tabs/android-native-avatar-original.png).

For a circular avatar, prepare an image with transparent corners. For a selected ring, prepare a second transparent image containing that ring; neither a URI nor `renderingMode` crops a square photograph into a circle or adds a border. Keep both states on an equal-sized canvas. Start with a bundled small PNG to separate rendering from loading, then test the remote equivalent and a failed/missing-image fallback. Metro `require` assets already carry size/scale metadata, but the underlying asset must still represent an appropriate logical icon size. SDK 58's Icon exposes no `borderRadius` style. [Expo image/icon contracts](https://docs.expo.dev/versions/v58.0.0/sdk/router/native-tabs/)

The Expo guide says Android image sources retain their original colors, but a controlled prepared-image trial exposed an installed SDK discrepancy: `react-native-screens` defaults `ImageSource` tinting to `tinted`; Expo's icon converter does not supply `original`. An explicit `unstable_nativeProps.android` override for `icon` and `selectedIcon` with `{ type: "imageSource", imageSource, tinting: "original" }` restored full color. This is a verified workaround using an unstable API, not a preferred production contract. The first uncontrolled yellow square alone was insufficient evidence; the later circular-image comparison established the discrepancy. [Expo rendering mode guide](https://docs.expo.dev/router/advanced/native-tabs/#icon-rendering-mode), [corrected Android evidence](../review-assets/native-tabs/android-native-avatar-original.png). Installed sources: `expo-router/build/native-tabs/utils/icon.js`, `NativeTabsView.shared.js`, plus the installed screens Android `ImageSource`/`NoTintDrawable` implementation.

This note corrects the capability conclusion. It does not by itself establish adoption readiness: guest Sign in reliability, accessibility, auth transitions and the remaining navigation/inset checks from the evaluation still apply. The bounded-source prototype passed Mobile TypeScript checking. No production source or dependency changes remain from this research.
