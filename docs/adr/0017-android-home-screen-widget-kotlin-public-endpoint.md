# Android Home-Screen Widget is hand-written Kotlin fed by the public profile endpoint

The **Home-Screen Widget** (see CONTEXT.md) renders the signed-in user's 30-day activity graph plus total on the Android home screen. Two load-bearing decisions were made.

First, the widget is implemented as a hand-written Kotlin `AppWidgetProvider` (bars drawn to a `Bitmap` via `Canvas`, delivered through RemoteViews), injected into the generated `android/` project by an Expo config plugin, with a tiny local Expo module bridging JS to the widget (handle/theme writes, update triggers). The alternative — `react-native-android-widget`, which renders TSX in a headless JS runtime — was rejected: every widget update would cold-start a JS runtime (battery and latency), and the library must keep pace with RN/Expo upgrades, a recurring compat risk for a component that should be maintenance-free. The honest cost is maintaining a small amount of Kotlin; the widget is deliberately simple enough (one bitmap, one count label, one placeholder state) to keep that cost bounded.

Second, the widget performs **unauthenticated** fetches against the existing public `GET /users/:handle/profile` endpoint. The app only writes the signed-in user's *handle* and theme preference to shared storage — no session token ever leaves the app's process. This is possible because the profile payload (including `activityLast30Days`) is already public, and it eliminates the hardest part of most widget builds: securely sharing credentials with a second process. Freshness comes from the Android 30-minute periodic tick plus app-triggered updates on watch log/remove, login, and logout. App-push-only freshness was rejected because it goes stale for watches logged from the web.

Consequences: the widget cannot ship via EAS Update (native code requires a new store build), and it shows the signed-in user's own graph only — an any-handle configurable widget is a separate feature, not an extension of this one.
